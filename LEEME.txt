BLACK ÓPTICA — BLACK OS

ESTADO
- Rama de trabajo: main.
- Black OS está conectado al proyecto Supabase BlackUsuario.
- Las sucursales canónicas son General Paz y Cerro de las Rosas.
- RRHH está integrado al portal.
- Black Fichada funciona como terminal separada y comparte la base de RRHH.
- El sistema de usuarios aplica permisos en frontend y backend.

ARQUITECTURA DE ACCESO
1. El administrador asigna módulos y funciones desde Sistema > Usuarios.
2. Los módulos no asignados no aparecen en el menú ni en los accesos rápidos.
3. Las funciones no asignadas se ocultan dentro de cada módulo.
4. Los iframes de módulos no autorizados no se cargan.
5. Supabase vuelve a validar permisos con RLS/RPC aunque se intente acceder manualmente.
6. El alcance de sucursales puede limitarse a General Paz, Cerro de las Rosas o ambas.
7. Los usuarios desactivados quedan bloqueados también desde la base, incluso con sesiones antiguas.
8. Altas, cambios de permisos y bajas quedan auditados.

BLACK FICHADA
- Edge Function: black-fichada-mark.
- Código servidor: supabase/functions/black-fichada-mark/index.ts.
- El PIN nunca se consulta desde el navegador.
- La hora se toma del servidor.
- La secuencia es entrada > salida > reingreso > salida.
- Las terminales usan credenciales independientes.
- Los secretos de terminal NO deben guardarse en GitHub.
- La administración se realiza desde RRHH, no desde el fichador.

SUPABASE
Las migraciones SQL están versionadas en /sql.
A partir de RRHH y del sistema granular de permisos, los cambios de esquema deben aplicarse mediante migraciones y quedar reflejados en el repositorio.

SEGURIDAD
- Nunca publicar SUPABASE_SERVICE_ROLE_KEY.
- La key publishable del frontend no reemplaza RLS.
- No guardar contraseñas de usuarios ni PIN en texto plano.
- No guardar secretos de Black Fichada en el repositorio.
- Todo módulo nuevo debe implementar permisos de interfaz + permisos de base.
- Los datos salariales de RRHH requieren permiso específico.
- Los cambios de usuarios quedan registrados sin almacenar contraseñas.

PERFORMANCE
- Los módulos del portal se cargan bajo demanda.
- Los índices de claves foráneas de las áreas activas fueron revisados.
- Las políticas RLS redundantes fueron eliminadas/optimizadas.
- No eliminar índices recién creados solo porque Supabase todavía los marque como no usados: necesitan carga real para acumular estadísticas.

PENDIENTE DE CONFIGURACIÓN EXTERNA
- Activar Leaked Password Protection desde Supabase Auth cuando esté disponible en el plan/configuración del proyecto.
- Probar al menos un usuario real restringido antes de extender el uso a todo el equipo.

REGLA PARA NUEVAS FUNCIONES
Antes de considerar lista una herramienta:
1. Debe aparecer solo a usuarios autorizados.
2. Debe ocultar acciones no autorizadas.
3. La base debe rechazar la misma acción si se llama fuera de la UI.
4. Debe respetar la sucursal del usuario cuando corresponda.
5. Debe dejar auditoría si modifica información sensible.
